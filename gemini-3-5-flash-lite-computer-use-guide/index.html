Using Computer Use with gemini-3.5-flash-lite: Setup and Pitfalls

Yes. In the Gemini API changelog entry for October 30, 2026, Google released the Computer Use tool to general availability (GA) across the Interactions and GenerateContent APIs. The official Computer Use documentation lists gemini-3.5-flash-lite as a supported model, described as a low-latency, cost-effective model supporting computer use; the model Google recommends first for computer use is gemini-3.8-flash. Two things to know up front: every example in the official documentation uses the Interactions API, with no generateContent example; and the model only returns the UI action to take, so clicking, typing and taking screenshots are your client's job. This page walks through enabling the tool, running the loop, scaling coordinates and answering safety confirmations, based only on Google's documentation.

What Computer Use is and who executes the actions

Computer Use is a built-in Gemini API tool. You send the task and a screenshot of the current screen, the model returns one suggested UI action (for example click at a coordinate, type some text, or navigate to a URL), your client actually performs it, sends back a fresh screenshot, and the loop continues until the task is done.

The documentation says you need to implement the client-side execution environment that receives and performs Computer Use actions. Your client parses the function_call, converts the normalized coordinates to screen pixels and executes the action. The model never touches your browser or computer directly; you provide the automation layer yourself. The official samples install google-genai and Playwright, and Google's reference implementation on GitHub (google/computer-use-preview) provides a Docker sandbox.

The documentation lists four supported models: gemini-4-argon, gemini-3.8-flash (described as the recommended model for computer use), gemini-3.5-flash-lite (a low-latency, cost-effective model supporting computer use) and gemini-3-flash-preview. The gemini-3.5-flash-lite model page also marks Computer use as Supported. Flash-Lite suits latency- and cost-sensitive routine automation; for flows where action accuracy matters most, Google points to gemini-3.8-flash first, so it is reasonable to run the same task set on both before choosing.

Timeline: on June 24, 2026 Google launched public preview support for Computer Use in Gemini 3.5 Flash, adding simplified actions with intents, built-in browser, mobile and desktop environments, configurable safety policies and prompt injection detection. On October 30 the tool became GA. The GA changelog entry does not mention any renamed tool or parameter, so follow the current Computer Use documentation. Sources: Gemini API changelog https://ai.google.dev/gemini-api/docs/changelog , Computer Use documentation https://ai.google.dev/gemini-api/docs/computer-use , gemini-3.5-flash-lite model page https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite .

Enabling it: add computer_use to tools and pick an environment

The official examples use the Interactions API: POST https://generativelanguage.googleapis.com/v1/interactions with the x-goog-api-key header. With the Python SDK you need google-genai 2.7.0 or higher and call client.interactions.create.

Add {"type": "computer_use", "environment": "browser"} to the tools array and set model to gemini-3.5-flash-lite. The environment can be browser, mobile or desktop, and each environment exposes a different set of actions.

Google states there is no need to specify the display size when issuing a request. The coordinates the model returns still have to be converted by your client to your actual screen size; see the coordinate section below.

Three optional fields appear in the documentation: enable_prompt_injection_detection (opt-in, default false), excluded_predefined_functions (remove some built-in actions) and disabled_safety_policies (turn off some safety policy categories). One JavaScript sample writes enablePromptInjectionDetection in camelCase while every other sample uses snake_case; when sending raw JSON over REST, use the snake_case names.

The Computer Use documentation does not show a generateContent request. Although the changelog says the tool is GA on both APIs, this page only describes the Interactions request shown in the documentation and does not guess generateContent field names.

The agent loop: each request returns only the next action

Google describes four steps. Step 1, send a request with the tool configuration, the task and the current screenshot. In the official loop sample, input is a list with a {"type": "text"} item for the task followed by a {"type": "image"} item holding the screenshot as base64 PNG with mime_type image/png.

Step 2, read the response. Its steps include items of type function_call, where name is the action and arguments holds the parameters. Every action also carries an intent string explaining what the step is meant to do; the documentation's example is a click with x 450, y 120 and the intent Click the search box to type the destination. The arguments may also include a safety_decision, covered in the safety section.

Step 3, your client scales the coordinates and performs the action. Step 4, capture a new screenshot and send the outcome back as a function_result. Each function_result has type, name, the call_id taken from the function call's id, and a result list with two parts: a text item (the official sample serializes the current url plus any error or acknowledgement as JSON) and an image item with the new screenshot. If the model returns several actions at once (parallel calls), you must send a function_result for each one in the next turn.

When sending results, set previous_interaction_id to the id of the previous interaction, put the function_result items in input, and include the same computer_use tool configuration again. Then go back to step 2.

The official Python sample caps the loop with turn_limit = 5 and stops when a turn returns no function_call, reading the final answer from the model_output steps. In production, set the turn cap to match task complexity so a confused agent cannot loop forever.

Scaling coordinates: the model works on a 1000 x 1000 grid

The action tables list x and y as int (0-999), and the loop description tells the client to scale them from the normalized 1000x1000 coordinates to your viewport. The documentation's helper computes the pixel x as int(x / 1000 * screen_width) and the pixel y the same way with screen_height. One sentence elsewhere on the page says the model predicts coordinates scaled to the screen; the sample code and action tables both use the 0-999 normalized form, so implement the scaling step.

Using the 1440 x 900 screen from the official example, a returned x 450, y 120 becomes a click at about 648 pixels across and 108 pixels down. The width and height you scale with should be those of the screen or viewport you screenshot and act on.

Do not feed the returned numbers straight into your automation as pixels. If clicks land away from the target named in the intent, first check that you applied the scaling and that the width and height match the screenshot you sent.

Browser actions include mouse actions such as click, double_click, triple_click, middle_click, right_click, move and drag_and_drop; keyboard actions type (text, press_enter default false), press_key and hotkey; plus scroll (direction and magnitude_in_pixels, default 300), navigate (url), go_back, go_forward, wait (seconds, default 1) and take_screenshot. Desktop has the same set without navigate, go_back and go_forward. Mobile has its own set including open_app, list_apps and long_press. In the official sample, when an action fails, the client returns {"error": message} as that action's result, and unknown action names trigger a warning; leave a handling branch for both in your own client.

Safety: answering require_confirmation and blocked

An action's arguments may include a safety_decision, for example decision require_confirmation with an explanation. Google's rule: if the decision is require_confirmation, prompt the end user; if the user confirms, set safety_acknowledgement in the function_result (the official sample sets safety_acknowledgement to true in the action result that is sent back with the text part).

If an action is blocked, Google says your client should halt the execution or handle the interruption. Do not work around it and keep going.

The safety policy categories are FINANCIAL_TRANSACTIONS, SENSITIVE_DATA_MODIFICATION, COMMUNICATION_TOOL, ACCOUNT_CREATION, DATA_MODIFICATION, USER_CONSENT_MANAGEMENT and LEGAL_TERMS_AND_AGREEMENTS. You can turn some off with disabled_safety_policies, for example ["data_modification"], but the documentation warns that the model may still return require_confirmation in some cases, so keep the confirmation flow in your client.

Prompt injection detection is supported by Computer Use for Gemini 3.5 Flash-Lite or later. It checks whether a screenshot contains hidden adversarial instructions and blocks execution when it finds them. It is opt-in with a default of false; set enable_prompt_injection_detection to true in the tool configuration. If the agent will browse pages whose content you do not control, it is worth considering.

Settings for running it on gemini-3.5-flash-lite

Thinking level: the documentation says lower thinking levels generally achieve a good balance for standard automation tasks. It gives no specific parameter value, so start low on Flash-Lite and raise the level only for multi-step pages where the agent makes mistakes.

Human hand-off: you can exclude built-in actions with excluded_predefined_functions (the official sample excludes click) and register a custom function such as yield_to_user, declared in tools like any normal function, so the model can hand control back when an action is unsafe or ambiguous.

Environment: Google recommends running the agent in a sandboxed VM or container isolated from your host, or at least a dedicated browser profile with limited permissions, starting each task from a known clean state, logging prompts, screenshots, suggested actions and safety responses, and preferring an allowlist over a blocklist. It also warns that Computer Use may contain errors and security vulnerabilities, and advises against tasks involving critical decisions, sensitive data, or actions where serious errors cannot be corrected.

How to confirm it works

First, run a small read-only task, such as opening a public web page and finding a link. The first response should contain a step of type function_call whose name is an official action like navigate or click, with an intent in its arguments. If you only get text back, check that the tool type is computer_use and that the model is on the supported list.

Second, perform the action and send back a function_result with the matching call_id and a new screenshot, together with previous_interaction_id. The next turn should return a new action. If the model repeats the same step, check that the screenshot was taken after the action and that coordinate scaling is correct.

Third, check the exit condition: the loop ends when a turn returns no function_call and only a text conclusion. Then test one action that needs confirmation, such as ticking a consent checkbox, and confirm your client stops to ask before acting and sends safety_acknowledgement after the user agrees.
