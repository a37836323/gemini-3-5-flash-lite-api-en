Moving from Gemini 2.5 to gemini-3.5-flash-lite: What to Change and How to Verify It

Google's Gemini API changelog entry for 2026-09-18 says access to the 2.5 models is now limited to users who have actively used them in the past. The models are not deprecated and will continue to be served until further notice, but new projects should use 3.5 Flash-Lite or 3.8 Flash. If a new project was going to use gemini-2.5-flash or gemini-2.5-flash-lite, or you want to move an existing project at the same time, switching to gemini-3.5-flash-lite means handling at least four things: thinking is on by default at the minimal level, tool calls and multi-step tasks need a higher level, sampling parameters such as temperature and candidate_count should be removed, and a request must not end with a prefilled model turn. Each item below follows Google's documentation and ends with a way to verify it.

What Google changed: 2.5 access is limited, new projects use 3.5 Flash-Lite

The source is the Gemini API changelog (https://ai.google.dev/gemini-api/docs/changelog), entry dated September 18, 2026: to protect capacity for existing workflows and new applications, access to the 2.5 models is limited to users who have actively used them in the past. These models are not deprecated and will continue to be served through the API until further notice. For any new projects, Google says to use its latest models, 3.5 Flash-Lite or 3.8 Flash.

The entry does not say which error a restricted account sees when it calls a 2.5 model, and this page does not guess at the error text. The practical effect is that a newly created Google project should not pick a 2.5 model; it should choose between 3.5 Flash-Lite and 3.8 Flash.

gemini-3.5-flash-lite became generally available on July 21, 2026, together with gemini-3.6-flash. The changelog describes it as a low-latency, highly cost-effective subagent option designed for high-volume automation. Google's page "What's new in Gemini 3.6 Flash and 3.5 Flash-Lite" (https://ai.google.dev/gemini-api/docs/whats-new-gemini-3.6) lists the recommended migration path to it as Gemini 3.1 Flash-Lite or Gemini 2.5 Flash, and calls it a strong migration path from Gemini 2.5 Flash. That page does not name 2.5 Flash-Lite separately, so if you are coming from 2.5 Flash-Lite, go through the parameter differences below one by one.

First check that gemini-3.5-flash-lite can handle your workload

The official model page (https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite) lists text, image, video, audio and PDF as inputs and text as the only output, with an input limit of 1,048,576 tokens and an output limit of 65,536 tokens.

Supported capabilities on that page are caching, code execution, file search, function calling, grounding with Google Maps, Search grounding, structured outputs, thinking and URL context; computer use is supported in preview. Audio generation, image generation and the Live API are not supported. Batch API, Flex inference and Priority inference are all supported.

So if you used a 2.5 model for real-time voice through the Live API, or to generate images or audio directly, you cannot simply swap the model name to gemini-3.5-flash-lite; you need a different model. If you only do text, document parsing, extraction, classification and tool calls, follow the sections below. Google positions the model for subagent tasks, document parsing, high-volume agentic workflows, simple data extraction, and applications where latency and API cost are the primary constraints.

Thinking level: minimal by default, raise it for tool calls

This is the clearest difference from 2.5 Flash-Lite. In the model table on Google's thinking page (https://ai.google.dev/gemini-api/docs/thinking), gemini-2.5-flash-lite has thinking off by default, while gemini-3.5-flash-lite has it on at the minimal level, with minimal, low, medium and high as the supported levels; the table does not list an off option. The same page says a thought signature is always present, even when the model performs only minimal reasoning.

The migration checklist asks you to replace thinking_budget with thinking_level instead of setting a token budget. The examples on the thinking page set thinking_level inside generation_config. If you use a different request format, check the field name in the official API reference for that format.

For choosing a level, the checklist says to keep minimal (the default) for high-volume extraction, routing or classification, and to use medium or high for autonomous subagents with tool calls, code execution or multi-step reasoning, to prevent premature tool termination. Elsewhere the same page advises increasing the thinking level for autonomous planning and complex subagent tasks, and experimenting with both minimal and high for documents, depending on document complexity.

So if code that ran function calls on 2.5 Flash-Lite without thinking now stops before the tool chain finishes, follow Google's advice: raise thinking_level to medium or high and test again.

Parameters to remove: temperature, top_p, top_k and candidate_count

The "Sampling parameter deprecation" section of the what's-new page says temperature, top_p and top_k are deprecated and ignored, and that in future model generations supplying them returns an HTTP 400 error. Google's instruction is to remove these parameters from all requests.

In other words, after switching to gemini-3.5-flash-lite these parameters do not cause an error yet, but they no longer have any effect. If you relied on temperature 0 for stable output, Google suggests defining a system instruction with explicit rules for your use case instead.

The checklist marks candidate_count as unsupported in Gemini 3 and later, so code that asks for several candidates in one response needs to change. The page does not say which error is returned if candidate_count is sent.

A prefilled model turn returns 400

The "Prefilled model turn validation" section says prefilling model turns is no longer supported: if the last non-empty turn in the request is a model turn, the API returns a 400 error. In the 2.5 era some code placed a model-role message at the end of contents to make the model continue from a fixed opening or a JSON prefix. That pattern is rejected on gemini-3.5-flash-lite.

Google's replacement is to use system_instruction or structured outputs (https://ai.google.dev/gemini-api/docs/structured-output) if you used prefilling to suppress preambles or force JSON. After the change, make sure the last non-empty turn in contents is a user turn or a function result.

The Flash-Lite checklist also says to apply the same function calling rules as 3.6 Flash. If you see Malformed_Function_Call errors tied to pre-tool text, the function calling guide has a dedicated section (https://ai.google.dev/gemini-api/docs/function-calling#workarounds-for-pre-tool-text-requirements).

Multi-turn and tool calls: send thought signatures back unchanged

Thought signatures are a baseline requirement for Gemini 3.x, and the checklist points to them. The thinking page says that in stateless mode you must always resend all thought blocks exactly as they were received, and must not remove or modify them in the history. When switching models within a session you should still resend the previous model's thought blocks. Built-in tools such as Google Search can carry their own signatures, and in stateless mode those tool result signatures must also be resent in later turns.

In the generateContent API reference (https://ai.google.dev/api/generate-content), Part.thoughtSignature is described as an opaque signature for the thought so it can be reused in subsequent requests, and FinishReason includes MISSING_THOUGHT_SIGNATURE, meaning the request has at least one thought signature missing. If your code rebuilds the conversation history itself, check during migration that the parts carrying signatures are kept.

How to verify the migration

Step 1: confirm the model name is now gemini-3.5-flash-lite and that it appears in the model list (through OpenLux, call /v1/models).

Step 2: send a minimal request in which the last non-empty turn is a user turn, with no temperature, top_p, top_k or candidate_count, and with thinking_level as the only thinking parameter. A normal text response means the request structure is fine.

Step 3: confirm the thinking level takes effect. In the generateContent response, usageMetadata.thoughtsTokenCount is the number of thinking tokens (the Interactions API used in Google's thinking examples reports total_thought_tokens instead). Run the same prompt once with minimal and once with high and compare the counts.

Step 4: run regression tests on your real samples. For extraction and classification, check that the output still meets your existing parsing rules. For tool calling, run a full multi-turn exchange and confirm the tool chain completes and finishReason never shows MISSING_THOUGHT_SIGNATURE; if needed, raise the level and compare again.
